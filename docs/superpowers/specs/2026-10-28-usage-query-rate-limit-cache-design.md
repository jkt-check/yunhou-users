# Usage 查询限流与短缓存设计

## 目标

支持同一用户同时打开 10 个 Usage 页面：每页每 5 秒最多 8 个查询，持续运行时看板查询不因限流返回 429，同时避免相同页面请求重复打到 PostgreSQL。

## 决策

采用 **20 QPS / burst 100 + 5 秒进程内缓存 + 相同请求并发合并**。

不采用 5 QPS / burst 50：限流位于缓存之前，缓存命中也消耗令牌；10 页面产生 16 QPS HTTP 请求，5 QPS 会在初始突发耗尽后持续限流，无法满足两分钟无 429 的验收条件。20/100 解决 HTTP 准入，缓存与并发合并解决 DB 重复查询，两者不能互相替代。

## 范围

- `summary`、`breakdown`、`timeseries`、`GET /user/devices` 共用按 JWT `user_id` 分桶的 20 QPS / burst 100。
- `coverage` 拆成独立的 1 QPS / burst 30 用户桶，保持现有限流能力，不缓存，避免看板流量影响上传前的配置发现。
- batch/backfill/export/删除/设备写的限流配置、请求和响应契约均不变。
- 不修改令牌桶实现，不修改 Website，不新增全局 QPS 限流。现有 PostgreSQL `MaxOpenConns=25` 继续作为 DB 连接保护。

## 缓存

新增仅供这些 Usage GET 路由使用的 Gin 响应缓存中间件：

- key 包含 `user_id`、路由模板、规范化后的查询参数、5 秒时间桶和用户缓存代次。
- 规范化查询参数时对参数名和重复参数值排序，使语义相同但参数顺序不同的请求共享缓存。
- 仅缓存完整成功的 HTTP 200 JSON 响应；非 200、错误和覆盖配置发现语义的 coverage 不进入缓存。
- 相同 key 的并发 miss 只有一个 leader 执行下游 handler，其余请求等待并共享结果，不为每个等待者重复访问 DB。
- 缓存条目最多存活到当前 5 秒时间桶结束，定期清理过期条目和完成状态。
- 缓存为进程内实现；多实例之间不共享，允许最多 5 秒的数据延迟。

## 写后失效

以下操作成功后使用户缓存代次递增，后续查询不再命中旧代次：

- batch 和 backfill 上传成功；
- Usage 删除成功；
- 设备注册、重命名、撤销/purge 成功。

失败请求不失效。代次也参与 key，避免“查询在写操作前开始、写后失效、旧查询随后又写入缓存”的竞态。多实例只保证本实例立即失效，其他实例仍在 5 秒 TTL 内自然过期。

## 中间件顺序

JWT 鉴权 → 对应的用户限流器 → Usage 查询缓存（仅 GET 查询）→ handler。

写路由使用独立的成功后失效中间件，不经过查询缓存。429 仍由现有限流器返回，响应体与 `Retry-After` 行为不变。

## 验证

- 缓存命中、参数规范化、用户/路由隔离、TTL 过期、错误不缓存。
- 80 个相同并发查询只执行一次下游；不同查询参数保持独立。
- 写成功失效、写失败不失效，以及写期间完成的旧查询不能复活旧缓存。
- 新用户同步 80 个查询无 429；持续明显超过 20 QPS 在令牌耗尽后返回 429 且带合理 `Retry-After`。
- coverage 与看板桶互不影响；上传及其他限流数值不变。
- 10 页面、每页每 5 秒 8 查询、持续至少 2 分钟无 429/5xx，并观察 PostgreSQL 连接数、查询耗时和 Users CPU。
- 运行 `go test -race` 相关测试、`make test`、`make lint` 和 `make build`。机器高负载时以实际测试输出判断失败，不把运行缓慢当作失败。
